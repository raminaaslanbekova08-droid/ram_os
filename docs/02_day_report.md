 Итоговый отчёт за день 2

 Тема

Определение типов данных для полей базы данных системы оформления заказа обуви, сопоставление типов SQLite с типами из задания демонстрационного экзамена, создание черновой базы данных и работа с ней.

 Цель работы

Научиться определять типы данных для каждого поля таблицы, сопоставлять типы SQLite с типами из списка демонстрационного экзамена (INTEGER, VARCHAR, DATE, NUMERIC), обосновывать выбор типа, создавать черновую базу данных с ограничениями и проверять её работу через SQLite Viewer и Python-скрипты.

 Что сделано

1. Выписаны все поля всех семи таблиц: `roles`, `users`, `products`, `sizes`, `stock_items`, `orders`, `order_items`.
2. Определены типы данных SQLite для каждого поля.
3. Составлено сопоставление типов SQLite и типов из демоэкзамена (`INTEGER`, `VARCHAR`, `DATE`, `NUMERIC`).
4. Определены ограничения для каждого поля (`NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`, `PRIMARY KEY`, `FOREIGN KEY`).
5. Проверена схема именования (латиница, нижний регистр, snake_case, суффикс `_id`).
6. Создана черновая база данных `db/shoe_store.sqlite`.
7. Проверены ограничения на практике — все 7 тестов пройдены.
8. База заполнена тестовыми данными: 3 роли, 3 пользователя, 5 товаров, 5 размеров, 10 товарных позиций, 3 заказа, 6 позиций заказов.
9. Написаны простые SQL-запросы (5 шт.) для проверки данных.

 Принятые решения и их обоснование

 Почему INTEGER для идентификаторов

Целые числа быстрее и компактнее, поддерживают `AUTOINCREMENT`. Это стандарт для первичных и внешних ключей. Также INTEGER быстрее, чем TEXT, при поиске и соединении таблиц.

 Почему TEXT для дат

В SQLite нет отдельного типа `DATE`. Формат ISO 8601 (`YYYY-MM-DD`) корректно сортируется как строка (лексикографический порядок совпадает с хронологическим) и совместим с типом `DATE` из демоэкзамена.

 Почему NUMERIC для цен

Цены в рублях требуют точности до копейки. `NUMERIC` хранит число с фиксированной точностью и не даёт накапливаться ошибкам округления, в отличие от `REAL`.

 Почему login должен быть UNIQUE

Система различает пользователей по логину. Дубликат логина сделал бы невозможной однозначную идентификацию пользователя при входе и при связывании с заказами.

 Почему order_date имеет DEFAULT

Большинство заказов создаётся «сегодня». `DEFAULT CURRENT_DATE` избавляет от необходимости каждый раз указывать дату вручную и предотвращает NULL в обязательном поле.

 Почему RESTRICT для заказов и CASCADE для состава заказа

- **RESTRICT** на `orders.user_id`: нельзя удалить пользователя, пока у него есть заказы — это защита истории.
- **CASCADE** на `order_items.order_id`: при удалении заказа его позиции не имеют смысла и должны удаляться автоматически.
- **RESTRICT** на `stock_items.product_id` и `stock_items.size_id` — чтобы случайно не потерять связанные данные о товарах и размерах.
