 1. Защита от SQL-инъекций
В приложении строго запрещено использовать f-строки (`f"SELECT ... {var}"`) или конкатенацию (`+`) для передачи данных в SQL-запросы.
**Правило:** Всегда используются параметризованные запросы с плейсхолдерами `?`.
```python

cursor.execute("SELECT * FROM users WHERE login = ?", (user_login,))


 Краткие ответы на вопросы (День 13)

1. **Что такое SQL-инъекция?** 
   Внедрение вредоносного SQL-кода через пользовательский ввод, из-за чего злоумышленник может изменить логику запроса (например, обойти авторизацию).
2. **Почему f-строки опасны?** 
   Они смешивают код и данные. База данных воспринимает введенный текст как продолжение команды.
3. **Как параметризация защищает?** 
   Запрос и данные передаются раздельно. База обрабатывает данные как простой текст, а не как исполняемый код.
4. **Почему нельзя хранить пароли открыто?** 
   При взломе базы (утечке) злоумышленник получит доступ ко всем аккаунтам.
5. **Что такое хэширование?** 
   Математическое преобразование пароля в строку фиксированной длины (хэш). Из хэша невозможно восстановить исходный пароль.
6. **Как проверить пароль с хэшем?** 
   Взять введенный пароль, прогнать его через ту же функцию хэширования и сравнить результат с хэшем в базе.
7. **Суть принципа минимальных привилегий?** 
   Пользователь должен иметь только тот доступ, который строго необходим ему для работы.
8. **Зачем нужен `login_audit`?** 
   Для логирования попыток входа, чтобы можно было обнаружить подозрительную активность (например, тысячи неудачных входов).
9. **Что будет при получении доступа к файлу SQLite?** 
   Злоумышленник сможет прочитать, изменить или удалить данные, так как в SQLite нет защиты паролем на уровне самого файла.
10. **Как защитить файл БД?** 
    Ограничить права доступа на уровне файловой системы (chmod 600), использовать шифрование диска, не выкладывать файлы БД в открытые репозитории.
